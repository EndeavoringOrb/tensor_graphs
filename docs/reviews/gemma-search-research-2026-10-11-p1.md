Mathematical Objective and Bucket Weight SemanticsLet $\mathcal{B} = \{0, 1, \dots, B-1\}$ denote the set of execution buckets registered in the compilation session. Each bucket $b \in \mathcal{B}$ represents a distinct dynamic execution context defined by dirty input regions $\mathcal{R}_{\text{in}}^{(b)}$ and required output regions $\mathcal{R}_{\text{out}}^{(b)}$. The global optimization objective evaluated across complete leaf states in SearchEngine::solve is the weighted sum of bucket makespans:$$\min \quad \Phi = \sum_{b \in \mathcal{B}} w_b \cdot \mathcal{M}_b(\mathbf{S}_b, \mathbf{T}_b)$$where $w_b \ge 0$ is the normalized frequency weight assigned to bucket $b$ such that $\sum_{b \in \mathcal{B}} w_b = 1.0$, $\mathbf{S}_b$ denotes the vector of chosen operation implementations, $\mathbf{T}_b$ denotes their scheduled dispatch ranks, and $\mathcal{M}_b$ is the parallel execution makespan computed by MakespanSimulator.In language model compilation sessions managed through LLMSession, two primary modes configure these buckets:Full Sequence Mode (--config full): Evaluates a single full-sequence bucket covering input tokens $[0, \text{max\_seq\_len}]$ and logit projections $[0, \text{vocab\_size}]$, assigned an exclusive weight of $w_0 = 1.0$.Decode Step Mode (--config decode): Registers $N = \text{max\_seq\_len}$ individual single-token dirty slices ($i \in [0, N-1]$) with positive weights, and automatically appends an all-inclusive full bucket via Session::ensureFullBucket. When user-defined decode buckets exist, Session::updateFullBucketWeight explicitly sets the full bucket weight to $w_{\text{full}} = 0.0$.A weight of zero does not exempt a bucket from search. The full bucket must yield a feasible plan that satisfies all memory limits, operator precedences, and cache commitments. It acts as a global feasibility witness, ensuring that persistent buffer layouts and cache states produced during decoding remain compatible with complete sequence recomputation.Dispatch Rank Versus Physical Elapsed TimeA foundational distinction in the planner architecture is that the decision variables $\mathbf{T}_b = \{T_{b, c}\}$ for an equivalence class $c$ represent discrete dispatch ranks (topological ordering steps), rather than continuous physical time coordinates. The search space assigns integer ordering indices:$$T_{b, c} \in \{0, 1, \dots, |\mathcal{C}_b| - 1\}$$where $\mathcal{C}_b$ is the set of reachable equivalence classes in bucket $b$.The actual physical execution timeline is evaluated post hoc by MakespanSimulator inside SearchEngine::evaluateMakespan. The simulator traverses active operations sorted by ascending dispatch rank ($T_{b, c}$) and computes physical completion times:Operations of type INPUT and CACHE are assigned duration $0.0$ and finish time $0.0$.Non-view computational operations retrieve kernel durations $\tau(e, k)$ from bucket_enode_infos. View operations (is_view == true) have zero physical duration.For each computational kernel assigned to hardware engine set $\mathcal{E}_k$, physical dispatch time is constrained by both data dependency and engine readiness:$$t_{\text{start}}(c) = \max \left( \max_{p \in \text{children}(c)} t_{\text{finish}}(p), \quad \max_{e \in \mathcal{E}_k} t_{\text{avail}}(e) \right)$$$$t_{\text{finish}}(c) = t_{\text{start}}(c) + \tau(e, k)$$$$t_{\text{avail}}(e) \leftarrow t_{\text{finish}}(c) \quad \forall e \in \mathcal{E}_k$$The makespan $\mathcal{M}_b$ is $\max_{e} t_{\text{avail}}(e)$. Because dispatch ranks merely specify serialization order, a numeric rank difference $T_{b, c_2} - T_{b, c_1} > 1$ introduces zero physical execution delay if the operations run on disjoint engines or if data dependencies allow concurrency. Conversely, two operations assigned adjacent dispatch ranks on the same unary engine are serialized in time.Variable Types and Restoration MechanicsThe search state space is parameterized by four distinct variable families registered across buckets:Variable FamilyIdentifierScopeDomain SemanticsCACHEDcached_<base_id>GlobalBinary: $\{0\}$ (uncached) or $\{1\}$ (cached across buckets).SELECTEDselected_<b>_<cid>Per-BucketDiscrete: $\{0\}$ (unselected) or $\{1 \dots K\}$ (active e-node candidate).STARTstart_<b>_<cid>Per-BucketDiscrete rank: $[0, \text{max\_rank}]$ specifying dispatch sequence.OFFSEToffset_<b>_<cid>Per-BucketInteger page: $[0, \text{max\_pages}]$ specifying memory base offset.The search engine explores this space using a trailing mechanism (SearchState::trail).
