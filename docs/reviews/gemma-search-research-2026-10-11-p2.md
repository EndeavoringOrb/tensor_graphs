## Executive summary

The most valuable findings are not all new propagators:

1. **There is a real search-coverage hazard in offset branching.** `HeuristicBrancher::setOffsetDecision` chooses `offset=preferred` versus `[preferred+1,max]`; for an interior preferred address, it omits every smaller address. The omitted values are not necessarily impossible: `preferredOffset` treats a safe in-place producer allocation as an obstacle even though the memory propagator explicitly permits that overlap. This can lose a feasible—and potentially uniquely feasible—plan. Repair/justify this before claiming global optimality.
2. **The cache-packing concern needs a more careful verdict than the prior review gave it.** `CachedOffsetAllocationPropagator` does deterministically append caches rather than branch over arbitrary layouts. But the review’s specific “preallocated buffer at page 100 leaves pages 0–99 free” example is not produced by this planner: `Planner::preallocate` packs preallocated inputs contiguously from offset 0. Under a common-prefix, contiguous-domain invariant, sequential cache packing can be a complete canonical placement. The source does not yet prove that invariant for every view/fixed-offset state, so preserve the issue as an exactness proof obligation, not a confirmed Gemma failure.
3. **A major scaling problem is statically visible at 262,144 buckets.** `SearchState::updateLowerBoundBucket` rescans all B bucket bounds; each of the critical-path, engine-workload, and start-run initializations calls it once per bucket. That is Θ(B²) work per initializer at the root. `Planner::planAll` also does a pairwise duplicate-bucket scan with Θ(B²) worst-case comparisons. These are source-derived operation counts, not timings.
4. **Two useful objective bounds are demonstrably weak before choices are fixed.** Critical path treats a class that can still be unselected as cost zero, including when a parent alternative would require it. Engine workload counts only a fixed positive selection. Conditional critical path and minimum mandatory work per modeled engine are admissible strengthening opportunities.
5. **The prior claim that Hall-interval propagation is missing is false for this snapshot.** `StartBoundsPropagator` already performs mandatory-start Hall bounds propagation and is registered in `addBasePropagators`. Its source tests include small exhaustive/randomized checks, optional-task activation, masks, and a 20,000-start stress case. Do not reimplement it; inspect/measure it if rank branching is a bottleneck.
6. **Bucket decomposition is mathematically promising only after conditioning on the full shared interface.** With all cache bits and persistent cache addresses fixed, the visible remaining schedule/selection/scratch-offset constraints are bucket-local and the objective is additive. Zero-weight full buckets still require a feasible witness. No neighboring-sequence-length choice may be fixed without equivalence or dominance proof.

No performance speedup estimate is asserted. The supplied test uses sequence length 16; the requested future target of 2×131,072 decode/prefill buckets is not generated by the included `LLMSession` decode loop, which currently builds one bucket per token plus a full bucket.

## 3. Priority 0 — protect search-space coverage

### 3.1 Offset branching can discard valid addresses

`preferredOffset` collects fixed-offset obstacles and returns the first free address it sees (`brancher.hpp:431–646`). `setOffsetDecision` then sets:

- left: `{preferred}`
- right, when `preferred < max`: `[preferred+1,max]`

(`brancher.hpp:648–665`). If `preferred > min`, the interval `[min,preferred-1]` is absent from both children. This is not automatically sound just because `preferredOffset` called those addresses obstacles: the brancher’s obstacle scan does not apply the full `canShare`/safe-in-place test used by the memory propagator.

**Concrete source-semantic counterexample (page units).** Let producer A have fixed offset 0 and size 2, consumer B have size 1 and offset domain `[0,3]`, and let B’s selected kernel declare A’s input slot safe for in-place use. Fix A’s start at 0 and B’s at 1. The memory propagator permits B at 0 or 1 inside A’s `[0,2)` buffer: `canReadInPlace` checks the safe input index and containment (`memory_no_overlap.hpp:1374–1398,872–913`). In `preferredOffset`, A is a fixed obstacle and B’s start overlaps A’s lifetime; the obstacle scan does not test safe-in-place reuse, so it advances the candidate to page 2. `setOffsetDecision` explores `{2}` and `[3,3]`, omitting valid pages 0 and 1. Now let a required root operation consume B, have size 2, start at rank 2, and share the four-page arena. Its only range disjoint from A is `[2,4)`, which conflicts with B at 2 or 3; B at 0/1 can safely share A and leaves `[2,4)` for the root. The current brancher assigns active offsets in topological order (`brancher.hpp:983–1005`), so when B is chosen before the root offset is fixed, the root is not yet among `preferredOffset`’s fixed obstacles. The feasible layout is A=0, B=0 (safe in-place), root=2. The later root offset propagation can validate it. The branch tree can lose this completion.

This is a **generic supported-semantics counterexample**, not evidence that a safe-in-place Gemma alternative survives the omitted kernel registry. The exact Gemma reachability question is open because kernel implementations are excluded. It is sufficient to show that the generic exactness argument is missing.

**Soundness condition.** Dropping every address below `p` is sound only if the propagator proves, in the current branch, that every such address is infeasible for the target under all surviving choices—including views and safe in-place relations. Otherwise branch over a complete partition. For interval domains, a simple binary partition such as `[lo,p]` versus `[p+1,hi]` covers the parent; a later split can isolate `p`. Do not use a preferred value as an implicit proof of infeasibility. If future offset propagators create mask holes, also preserve the parent domain: `setDomain` replaces domains, while the right delta is constructed as a range (`search_state.hpp:1153–1185`; `brancher.hpp:655–662`). Current offset propagators appear mostly bound-oriented, so reachability of mask-valued OFFSET domains is not established.

**Exactness impact:** potentially incomplete search and missed optimum, not merely a different branch order.

### 3.2 Arrival-order cache packing: reject the prior counterexample, retain the proof obligation

`CachedOffsetAllocationPropagator::allocateCachedOffset` picks one address and fixes every bucket copy; it does not enumerate alternative cache layouts (`cached_offset_allocation.hpp:68–171`). That is a policy restriction unless the packing is proved canonical. But the earlier review’s specific example—one preallocated buffer at pages `[100,160)` with free pages `[0,100)`—does not follow from the provided planner path:

- `Planner::preallocate` sorts entries and assigns each next preallocated input at the current per-space cursor, beginning at 0, with page-aligned sizes (`planner.hpp:306–337`).
- `preallocated_pages` is the maximum preallocated end (`planner.hpp:2247–2254`).

Thus the generated preallocated inputs occupy a contiguous prefix `[0,P)`; there is no unused hole below P in this path. The earlier `[100,160)` example is not a source-generated counterexample unless an omitted/custom preallocator injects such an offset.

**Sufficient condition for a complete canonical pack.** For one memory space, suppose all non-aliased cached objects are mutually non-overlapping persistent buffers with sizes `s_i`, every feasible address domain is exactly a full interval `[P, cap-s_i]` after the contiguous preallocated prefix, and there are no other fixed-address, view-alias, or bucket-specific restrictions. A sequential assignment in any order at `P + Σ_{j before i}s_j` is feasible iff `P+Σ_i s_i ≤ cap`; any feasible packing also requires that total-space inequality. In this restricted case the deterministic append order does not lose a feasible cache placement.

**Why a proof is still needed.** The implementation handles fixed offsets specially, otherwise appends each new cache after every already fixed cached object and fails if that one candidate exceeds the common upper bound (`cached_offset_allocation.hpp:78–109,112–169`). It does not search gaps or change order. For arbitrary allowed domains, it is not complete. Example: cap 100, A size 60 with allowed starts `[20,40]`, B size 40 with allowed starts `[0,60]`. If A is assigned first, the routine picks A=20 then tries B=80 and fails; B=0, A=40 is a feasible non-overlapping packing. This is a counterexample for nonuniform cache domains; the provided source does not establish that such a state is reachable in the target Gemma run. A fixed-address version is similar: a 20-page cache fixed at 80 followed by an 80-page cache with starts `[0,20]` is feasible at 0/80, while append-after-fixed tries 100 and fails.

**Decision:** do not label the p1 preallocation-hole example as confirmed. Do not claim cache packing is exact either. First assert/verify the common-prefix interval invariant for every cached base copy after view/cache propagation. If it holds, document the proof and test it. If it fails, treat the current routine as an exactness restriction and use complete placement search or a proven alias-aware packing policy.

## 4. Priority 1 — remove source-visible quadratic bucket overhead

### 4.1 Weighted lower-bound recomputation

`SearchState::updateLowerBoundBucket` updates one bucket’s bound, then resets and recomputes the weighted sum by scanning every bucket (`search_state.hpp:930–953`). Each of these initial paths calls it once per bucket:

- `CriticalPathPropagator::initialize` (`critical_path.hpp:150–158`)
- `EngineWorkloadPropagator::initialize` (`engine_workload.hpp:30–38`)
- initial `StartRunMakespanPropagator::propagate` (`start_run_makespan.hpp:463–472`)

So each full initialization has Θ(B²) bucket-entry work. At B=262,144, that is **68,719,476,736 bucket-entry visits per initializer**; three such initializations are about **206,158,430,208 visits** if all run on the root path. This is a static loop count, not a runtime estimate. The same method is Θ(B) for every later single-bucket update.

Maintain the total by delta, `LB_total += w_b·(new_LB_b−old_LB_b)`, and compute the initial total once after all bucket components are initialized. Ensure the accumulator stays correct through propagation batches and backtracking; periodically recompute from the vector in debug/testing builds to catch drift. Zero-weight buckets still maintain local feasibility state but contribute zero to the aggregate.

### 4.2 Duplicate bucket reporting

Before saturation, `Planner::planAll` compares each bucket with all earlier buckets to log an “identical to bucket” note (`planner.hpp:1972–1991`). If all buckets differ, this is B(B−1)/2 comparisons: **34,359,607,296** at B=262,144. The current decode loop gives each slice a different token coordinate (`bindings.cpp:410–417`), so those bucket descriptors are distinct in the ordinary case. At sequence 131,072, the included binding produces 131,072 token buckets plus a full bucket (131,073 total), not 262,144; the corresponding all-distinct scan is 8,590,000,128 comparisons.

Replace diagnostic pairwise search with a canonical hash table and exact equality confirmation. The hash should cover the full dirty-input and needed-output region descriptions, not only sequence length or bucket index.

### 4.3 Global invalidation / repeated per-bucket setup

A selection change increments one global `selection_revision` (`search_state.hpp:763–782`). On a revision change, `chooseSchedule` clears/rebuilds topo-order data across all buckets (`brancher.hpp:831–940`). Make this bucket-local. Likewise `CacheFreshnessPropagator::ensureIndex` scans every cached base and then every bucket’s selection map (`cache_freshness.hpp:15–39`); build the base-to-selection reverse index in one pass over selections. `planAll` stores and saturates an EGraph for each bucket (`planner.hpp:2008–2018,2266–2291`); duplicate logging does not reuse those graphs.

At B=262,144, changing one local selection can therefore trigger work proportional to the full bucket family, and host memory grows with the sum of per-bucket graph/state sizes. The number of classes/enodes per bucket is absent, so no RAM number is asserted.

## 5. Priority 2 — strengthen admissible objective bounds before branching

### 5.1 Conditional critical path through optional children

Current `computeNodeCriticalPath` returns 0 as soon as a class’s selection domain contains 0 (`critical_path.hpp:99–134`). That is safe for an unconditional contribution, but weak when an active parent alternative requires the optional child.

For each bucket b and class C, let `A_C = {a : selected_C contains a and a>0}`. Define the conditional execution lower bound

`q_b(C) = min_{a∈A_C} [ d(a) + max( {q_b(D) : D is a child of a} ∪ {0} ) ]`.

For a leaf, the max over children is 0. When the dependency alternative graph is cyclic, retain a conservative cycle rule: treat a DFS back-edge as 0 (as the current code does at `critical_path.hpp:105–107`) or use another relaxation proved to under-estimate every finite acyclic completion. Do not infer infeasibility merely from a cyclic alternative edge; `CycleAvoidancePropagator` and selection propagation own that reasoning.

Because the root is required, a safe bucket lower bound is `max(q(root), max_{C mandatory} q(C))`, combined with other independently admissible bounds by `max`, not addition. The recurrence is sound because any completion selecting alternative a must execute every child, and its critical path is at least `d(a)+max(child path)`. The minimum over currently viable alternatives cannot exceed the path cost of the alternative actually selected. Shared children are safe: max-path aggregation does not charge a shared subgraph twice.

**Missed case.** Suppose the root has two remaining alternatives: `a1` costs 2 and requires child X whose conditional path is at least 80; `a2` costs 10 and requires child Y whose conditional path is at least 20. X and Y both still contain 0, so current CP sees the children as zero and returns 2. Conditional CP returns `min(2+80,10+20)=30`. An incumbent of 25 can then prune the state.

**Interactions and implementation guardrails:**

- A child is charged only conditionally when its parent alternative is being evaluated; do not add every optional descendant to the unconditional bucket bound.
- Count a shared e-class once in any additive workload sum; for path bounds use max, never sum child subtrees.
- Views and input/cache nodes use the same duration semantics as the leaf simulator: views have zero duration; INPUT/CACHE are zero-time. Their dependency edges still matter to a path.
- A multi-engine operation has one duration on a dependency path; engine contention is handled separately.
- Zero-weight buckets may compute q for diagnostics/feasibility reasoning but do not enter the objective sum.
- Backtracking must restore or recompute q values; do not retain a lower bound learned from a descendant domain.
- Match the simulator’s actual surviving-candidate and nonfinite-cost semantics. A nonfinite cost may be a pruned/unknown enode, not automatically a forbidden choice; the leaf simulator has its own handling (`types.hpp:1818–1821`).

A first implementation can recompute one affected bucket in O(V_b+A_b), where V_b is its reachable classes and A_b its alternatives. Incremental reverse-dependency updates may be worthwhile only after correctness tests; no runtime gain is assumed.

### 5.2 Minimum mandatory engine workload across viable implementations

Current `updateSelectedWork` adds cost only for a fixed positive selection (`engine_workload.hpp:87–109`). A mandatory class with two viable kernels contributes nothing until one is chosen.

For mandatory classes `M_b={C : 0∉D_C}`, let `E(a)` be the modeled engine set of alternative a, and let `d(a)` be its non-view duration. The simulator treats an empty engine list for a non-view operation as the CPU engine (`types.hpp:1847–1888`), so define `E(a)={CPU}` in that case. Views, INPUT, and CACHE contribute zero. For each modeled engine e,

`m(C,e) = min_{a∈A_C} ( d(a)·1[e∈E(a)] )`,  `W_b(e)=Σ_{C∈M_b} m(C,e)`,  `LB_engine(b)=max_e W_b(e)`.

For any actual completion, every selected operation’s load on e is at least its minimum contribution; the simulator serializes all operations assigned to e, so makespan is at least that engine’s accumulated duration. Thus the max across engines is admissible. Define d(a) using the leaf simulator’s effective duration for a surviving alternative; do not reinterpret `INF` as “impossible” unless the planner has removed that alternative. Charge a multi-engine operation’s duration to every engine in its modeled set, matching the simulator; do not invent physical concurrency or engine mappings. Classes are unique per bucket, so a shared child is not double-counted.

**Missed case.** Ten mandatory classes each have two viable CPU implementations of duration 3 and 5. Current fixed-only workload is 0 before implementation branching; the new CPU workload lower bound is 30.

Optional classes are excluded unless selection is forced; zero-weight buckets still need feasibility but not objective cost. Avoid counting a view as engine work even if its enode metadata contains an engine; the simulator sets view duration to zero. A stronger weighted-engine relaxation is possible, but should follow the basic bound and be independently proved.

### 5.3 Incumbent-driven cross-bucket candidate filtering

Existing search uses global lower bounds to prune a whole node (`search_engine.hpp:839–847`); it does not generally remove one candidate because of the weighted budget left by other buckets.

Let U be a **feasible** incumbent, `w_b>0`, and `L_j` valid bucket lower bounds under the current state. For a candidate literal c in bucket b, compute any admissible conditional bucket bound `L_b|c`. If

`w_b·L_b|c + Σ_{j≠b} w_j·L_j ≥ U`,

then no completion containing c can improve the incumbent. Equivalently, the current ceiling is `T_b=(U−Σ_{j≠b}w_jL_j)/w_b`; prune c when `L_b|c≥T_b`.

**Example.** Two buckets have weights 0.5/0.5, incumbent 100, and bucket 1 lower bound 80. A candidate in bucket 0 that implies a valid makespan bound of 130 gives total lower bound 105 and can be removed, although the current bucket-0 bound may be much smaller.

For a shared cache literal `CACHED_X=v`, evaluate/propagate the assumption across all affected buckets and prune v if `Σ_b w_b·L_b|v ≥ U`. A zero-weight full bucket gets no objective ceiling, but its local infeasibility under v can still eliminate v globally. If the full bucket is merely expensive, its cost alone cannot prune a zero-weight branch.

This preserves the optimal **objective value** given a feasible incumbent; pruning at equality can discard other optimal plans. Use `>` if all optima must be enumerated. Comparisons must be conservative with float costs, and an incumbent improvement must wake this filter even if no variable domain changed. For a local literal, the other buckets’ current bounds remain valid lower bounds under the added assumption; if shared propagation tightens them, use the tighter values.

## 6. Cross-bucket deductions: what transfers and what does not

### 6.1 Existing shared deductions

- `CACHED=1` removes zero from every matching per-bucket selection copy (`cache_freshness.hpp:53–80`); fixing a copy unselected removes the cached polarity (`:83–103`).
- Selecting a CACHE/SCATTER enode requires CACHED=1 (`cache_requirement.hpp:11–35`). CACHED=0 removes CACHE/SCATTER enodes across copies (`cache_exclusion.hpp:59–106`).
- Cache byte budgets are global by MemSpace (`cache_budget.hpp:20–41`; early pruning is in `early_cache_budget.hpp:45–109`). Before reusing those sums as a proof about distinct physical extents, verify that every pair of CACHED candidates represents distinct persistent storage: the memory model permits view aliases, while cache-budget accounting is by candidate bytes.
- When CACHED=1, corresponding offsets must agree; fixed addresses are copied across copies (`cached_offset.hpp:32–101`). The allocation propagator groups all bucket offset variables for each base (`cached_offset_allocation.hpp:14–29,68–109`).

A useful strengthening is a **conditional shared-offset domain**: while CACHED_X=1, the allowed address set is `D_shared(X)=∩_{b∈copies(X)}D_{b,X}`. Intersect every copy with this common set; if it is empty, remove CACHED_X=1 (or fail if already fixed). If CACHED is not fixed, keep the equality conditional—do not narrow offsets in the CACHED=0 mode. The current allocation routine intersects only min/max bounds and commits one candidate; it does not preserve a general sparse common-domain set or search another candidate after a failure. Current OFFSET domains are initialized as ranges and existing offset propagators mostly tighten bounds, so sparse-hole reachability must be checked before treating this as a Gemma hot path.

### 6.2 Exact factorization after the shared interface is fixed

Let g include every variable that occurs in constraints spanning buckets. In the visible native model this includes global CACHED bits and, when cached, the persistent shared addresses; include any additional shared/preallocated interface discovered by auditing the actual state. Conditional on g:

- SELECTED, START, and scratch OFFSET variables are bucket-indexed;
- precedence, rank uniqueness, cycle, start-run, and write-after-read reasoning are per bucket;
- the objective is additive, `Φ=Σ_b w_b M_b`;
- persistent/cache capacity and address equality have become fixed master facts.

If no other cross-bucket constraint remains, the exact problem is

`OPT = min_{g∈G : every bucket feasible} Σ_{b:w_b>0} w_b·OPT_b(g)`.

A zero-weight full bucket is a feasibility subproblem, not an optimization subproblem: it must have a witness for every accepted g. Shared children inside a bucket remain a local DAG issue; they do not couple two bucket schedules. Views and aliases must remain in each local subproblem unless their shared address is part of g. Scratch allocations from different buckets are treated as nonconcurrent by the current per-bucket memory model; confirm runtime semantics before changing that model.

This factorization is exact if the interface contains every cross-bucket variable and each local solve returns a certified optimum (or a valid lower bound plus feasible witness). It does **not** guarantee that the master is small: Benders/decomposition removes the Cartesian product of local schedules from one search tree, but may still enumerate many cache/interface assignments. Hooker’s work supports the method as a structure-dependent design choice, not a promised Gemma speedup [1](https://pubsonline.informs.org/doi/10.1287/opre.1060.0371), [2](https://www.cambridge.org/core/journals/knowledge-engineering-review/article/abs/logicbased-benders-decomposition-for-planning-and-scheduling-a-computational-analysis/70EE77BFAE516C56F3363A90A3786D84).

### 6.3 Reusable global cuts from local proofs

A local failure is reusable only if it proves the **entire bucket subproblem** infeasible under a sufficient set of interface assumptions—not merely that one branch of one local search failed.

If bucket b is infeasible under interface assignment g*, and an unsatisfiable core K of interface literals alone is sufficient for that infeasibility, the master may add the no-good `∨_{q∈K}(q ≠ g*_q)`. This is sound because every assignment matching K reproduces the proved local infeasibility. If the proof used a local literal such as `SELECTED_{b,C}=k`, that assumption must remain in the learned clause or be mapped through a proved bucket isomorphism; it cannot become a global cache-only cut.

For optimization, an exact local optimum at one g* gives a point-conditioned fact `g=g* ⇒ θ_b≥OPT_b(g*)`. It is not a lower bound for neighboring cache/address assignments unless a separate relaxation or dominance proof establishes that. Reuse a local nogood/cost cut in another bucket only when the local constraint graphs, costs, alias/view rules, and interface mapping are proved equivalent.

## 7. Equivalence, dominance, and warm starts are different

| Transfer type | What must be proved | Exactness effect |
|---|---|---|
| **Exact bucket equivalence** | A bijection of local feasible completions preserving objective costs, all bucket constraints, cache obligations, memory/alias semantics, and the global interface. A region/shape fingerprint must be canonical and include these properties. | Can solve one representative and transfer its exact result, with weights aggregated. |
| **Dominance** | For every completion using B, there is a feasible mapped completion using A with no larger total objective and identical external/interface effects. Cost alone is insufficient; engine sets, children, memory, view/in-place behavior, and cache production matter. | Can remove B while preserving optimal value, not necessarily all optimal plans. |
| **Warm start / value hint** | A candidate plan is checked feasible before it is used as an incumbent. | Does not remove the search space; cannot certify optimality by itself. |
| **Heuristic copying** | “Neighboring sequence lengths probably use the same kernel.” | Not a proof. Never fix a choice on this basis. |

`Planner::planAll` currently logs duplicate bucket descriptors but does not reuse their EGraphs or search results (`planner.hpp:1976–2018,2266–2291`). Exact identical bucket descriptions are a safe first template-grouping target within one fixed cost/settings context. A translation-invariant or sequence-family template needs a stronger proof: the Gemma graph has sequence-dependent positions and score tensors, and the full kernel/cost registry is absent. If only feasible sets are isomorphic but measured costs differ, share constraints/nogoods and re-optimize the local objective; do not transfer an exact optimum without re-evaluating it.

## 8. Priority 3 — memory feasibility before offsets are fixed

### 8.1 Concrete missed overload

In one bucket with a 100-page MemSpace cap, let two mandatory, non-view, non-alias temporary buffers have fixed selected enodes and sizes 60 and 50 pages. Their start/lifetime constraints require them both live at rank 5, and neither pair is eligible for safe in-place reuse. Leave only their offsets unfixed. Their individual offset domains can be `[0,40]` and `[0,50]`, so each fits alone; no pair of disjoint ranges can fit because 60+50>100. The current memory code collects these allocations but checks ranges against fixed allocations and explicitly defers unfixed/unfixed forward pruning (`memory_no_overlap.hpp:1194–1258,1261–1318`). A capacity overload can reject this state before choosing either address.

### 8.2 A sound compulsory-lifetime rule—and a correction to the earlier formula

For a mandatory allocation i with start domain `[l_i,u_i]`, let `R_i` be the set of **guaranteed** required reader classes: each such reader is mandatory and every remaining alternative reads i (including a selected view chain). This matches the intent of `allActiveAlternativesRead` (`memory_no_overlap.hpp:776–807`). Let `l_c` be reader c’s minimum start rank. In the discrete-rank memory model, a conservative compulsory-live interval is

`I_i = [u_i, E_i]`, where `E_i = max_{c∈R_i} l_c`, when `E_i≥u_i`.

Reason: every schedule has started i by u_i, and a required reader attaining the largest lower bound E_i cannot have run before E_i; i must remain available through that reader’s rank. The earlier review used `min_c l_c`; that is not the right end when several readers are guaranteed. If reader lower bounds are 2 and 10, the value is still required at rank 5 because the reader with lower bound 10 cannot yet have run.

For any rank t and a set S of allocations whose compulsory intervals all contain t, if every pair in S is provably non-shareable, then

`Σ_{i∈S} size_i ≤ capacity`

is necessary. Violation proves infeasibility. Views sharing one base count once; safe in-place producer/consumer pairs must not be counted as distinct if the implementation permits their contained overlap. If alternative enodes change the size, MemSpace, view status, or safe-in-place options, only count a lower-bound footprint/alias relation that holds for every surviving alternative; otherwise condition the check on the alternative.

**Caveat:** START is a dispatch rank, not physical time. This rule should be stated in the same rank/lifetime semantics as `MemoryNoOverlapPropagator`; do not turn ranks into kernel elapsed-time windows. If the runtime keeps a read buffer live until physical completion beyond the ordering rule represented by current memory propagation, that lifetime model is missing and must be resolved before claiming a physical-memory overload proof.

With an indexed guaranteed-reader graph, constructing endpoints and sweeping them is O(n log n) time/O(n) scratch per affected bucket. This is a design target, not an implementation measurement. First implement as a bound/failure rule for unambiguous mandatory non-alias buffers; extend to alternative/view/in-place cases only with separate tests.

## 9. Hall intervals are already present

The prior “add Hall-interval START propagation” proposal is stale for this source. `StartBoundsPropagator` is registered next to `StartUniquePropagator` (`propagator.hpp:78–81`) and enforces mandatory-start bounds consistency with forward/reverse Hall sweeps, while excluding optional classes (`start_bounds.hpp:7–9,150–161,216–254`). It accounts for fixed ranks by compressing occupied slots and states explicitly that masks are propagated by their interval hull, not by removing every interior hole.

The curated source contains `tests/start_bounds.hpp`: it enumerates small random interval cases and checks feasibility/bounds (`:7–52`), verifies optional-task activation (`:54–65`), and includes mask-hull and 20,000-start cases (`:121–183`). Those tests are present as source evidence only; this report did not execute them. If ranks remain a bottleneck, profile the existing Hall sweeps and precedence wakeups rather than adding a duplicate propagator.

## 10. Branching and search order (after bounds/coverage)

The brancher selects required e-class implementations, then cache decisions (candidate order, prefer 0), then cached offsets, then active starts/offsets, and finally optional selections (`brancher.hpp:1029–1129`; `chooseCache` at `:766–781`). This is a feasibility-first schedule, not a global impact comparison across buckets. The queue comparator switches from depth-first diving to `priority`; search constructs right priority as `parent LB+1` and left priority as `left LB−0.01·depth` (`search_node.hpp:42–58`; `search_engine.hpp:966–1002`). This affects exploration order, not completeness, provided every branch is complete and pruning is sound.

After exactness repairs and stronger bounds, useful experiments are:

- replace mixed raw-cost/depth constants with lexicographic fields (LB first after an incumbent, then depth/locality/tie-breaker);
- score global cache decisions by aggregate conditional objective-bound gain and feasibility impact across subscribers;
- probe both polarities for a small shortlist of high-fanout/high-bound-spread decisions, recording gain and propagation time;
- use feasible neighboring-bucket plans as **validated incumbents/value hints**, never as fixed choices.

Impact-based search literature motivates measuring the reduction caused by decisions; it does not predict gains for this planner [2](https://link.springer.com/article/10.1007/s13675-014-0026-3). Keep these heuristic changes separate from pruning and report first-incumbent time separately from proof time.

## 13. Correctness and performance checks

### Exactness / soundness

1. **Offset partition property:** Enumerate finite domains and every possible `preferred`; assert child domains are subsets of the parent, disjoint, and their union is the parent. Include wide ranges, short masks, and the safe-in-place producer/consumer/root case. The current implementation fails the union check when an interior preferred value drops a lower interval.
2. **Cache packer differential test:** For small page arenas, enumerate every legal address assignment under the same `preallocated_buffers`, max-per-base sizes, view aliases, fixed offsets, and memory limits; compare feasible cache sets with `allocateCachedOffset`. Include both the contiguous-prefix invariant case and nonuniform/fixed-domain counterexamples. If the invariant is the intended contract, assert it before sequential assignment.
3. **Bound invariants at every complete leaf:** For all buckets, check `q(root) ≤ simulated makespan`, `q(C) ≤ makespan` for every mandatory class, and `W(e) ≤ simulated makespan` for every logical engine e. Check weighted `LB≤Φ`. Include optional descendants, repeated/shared children, views, empty engine sets, zero-duration nodes, multi-engine alternatives, cycles in the alternative graph, and zero-weight buckets.
4. **Conditional objective pruning:** On tiny exhaustive instances, compare the best objective before/after every value deletion for all feasible incumbents. Confirm that equality pruning retains the objective value but may discard ties. Test incumbent improvement without domain change.
5. **Cross-bucket equivalence/decomposition:** Compare monolithic exhaustive search and master/local enumeration on small multi-bucket models with shared CACHED bits/addresses, cache freshness/exclusion, views, shared children, different local alternatives/costs, and a zero-weight full bucket. Validate every learned no-good against all master assignments.
6. **Backtracking:** Randomly branch, propagate, restore to arbitrary ancestors, and compare domains, reachability, shared address state, per-bucket bound components, and aggregate lower bound to a clean recomputation. The existing LCA replay makes stale incremental caches a primary risk.
7. **Memory overload:** Enumerate small rank/offset assignments for two/three buffers and compare with the compulsory-lifetime rule; include optional readers, a reader with multiple alternatives where only some read the buffer, views, safe-in-place, root/persistent allocations, and page boundaries. Count only a proven non-shareable set.
8. **Existing Hall tests:** The source includes `tests/start_bounds.hpp` with small exhaustive/randomized cases, optional activation, masks, and large-start cases; execute in the full repository before changing that propagator. These source tests were not run here.

OR-Tools can be a cross-check only for the subset represented identically by its export; do not treat the OR-Tools path as a full semantic oracle until cache addresses, views, memory reuse, engine sets, and bucket weights are confirmed to match.

### Performance telemetry (future run)

Use `tests/test_gemma_output.py --config full --optimal` and `--config decode --optimal` at the current sequence-16 baseline, then increase sequence and bucket counts. Record, with hardware/software and cost-model versions: preplanning/saturation time, root-propagation time, EGraph/state RSS, first feasible incumbent time, proof/exhaustion time, expanded nodes, per-propagator calls/time/domain reductions/conflicts, bound components, objective-value prunes, cache/offset decisions, and bucket-template counts. Separate “fewer nodes” from “cheaper nodes”; do not mix a feasible-output smoke result with an optimality claim.
